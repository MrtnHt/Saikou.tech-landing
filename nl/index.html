Controleer beveiligingsfixes van AI voordat je ze merget.

Een agent opent een pull request: "injectie opgelost". De scanner is het ermee eens, want de agent heeft er een nosec bij gezet. Saikou vergelijkt de code vóór en ná en blokkeert fixes die er alleen uitzien als een fix: een nieuwe onderdrukking, een opgeschoonde waarde die niemand gebruikt, één aanroeper gefixt terwijl de gedeelde sink rauw blijft, code vervangen door // ... existing code ....

Aan de slag Probeer het in je browser

v1.2.1 · Python 3.9+ · alleen de standaardbibliotheek · draait op je eigen machine · Apache-2.0 · geen score

Waarom een schone scan geen bewijs is

Statische analyzers respecteren onderdrukkingscommentaar. De goedkoopste manier om een bevinding te laten verdwijnen is haar dus het zwijgen op te leggen, en een voor/na-vergelijking van bevindingen meldt dan een verbetering. Vier stappen, waarvan één een leugen:

  1. De bevindingshell=True

    De scanner meldt een risico op commando-injectie.

  2. De "fix"+ # nosec B602

    De agent zet er een onderdrukking bij en verandert verder niets.

  3. De scan ernabevindingen: 1 → 0

    De scanner slaat de regel over, en het verschil leest als een fix.

  4. SaikouBLOCKED

    Het vergelijkt de code zelf: de sink is onveranderd en er kwam een onderdrukking bij.

Het ontbreken van een bevinding is nooit bewijs van een fix.

Zie het werken

Eén kwetsbaar bestand (SQL samengesteld met stringformattering, shell=True, MD5 voor wachtwoorden, path traversal) en drie voorgestelde fixes. De diffs, bevindingen en uitvoer hieronder komen van het echte commando, en de testsuite faalt zodra ze er niet meer mee overeenkomen; de bestanden staan in tests/fixtures/demo/. Kies een bevinding om de regel te zien waar ze naar wijst. De uitvoer van Saikou zelf is Engelstalig.

Zo lees je een rapport

Elke bevinding is één regel. Deze komt uit de nepfix hierboven:

HARD FAIL [parser] sink_shell_true L14: A fix for 'injection' was claimed but this sink survives unchanged: shell=True survives in the output; command injection sink intact.
HARD FAIL ernst
Een hard fail blokkeert het bestand. WARN wordt gemeld en blokkeert niet: iets om naar te kijken, zoals een directive voor de typechecker. Een bestand met minstens één hard fail is BLOCKED en het commando eindigt met 1 (0 = geen hard fail, 2 = fout), zodat CI erop kan poorten.
[parser] hoe het is vastgesteld
tool Een externe analyzer (bandit) leverde dit, twee keer gedraaid: normaal en met onderdrukkingen genegeerd.
parser Berekend door beide versies tot syntaxbomen te parsen en te vergelijken. Geen tekstgok.
mechanical Een deterministische tekst- of telcontrole. Betrouwbaar voor waar ze naar zoekt, blind voor betekenis.
sink_shell_true de check, en L14 de regel
Elke check heeft een id en een gewone beschrijving; de volledige lijst staat hieronder. Het regelnummer wijst in het bestand na de wijziging.
Verificatieniveau, per bestand
ast_verified Python: beide versies geparsed; API-oppervlak en sinks berekend, niet beweerd.
structural Geen parser: alleen tekstuele en structurele checks. Semantiek wordt niet geverifieerd.
asserted Onbekende taal: alleen basiscontroles. Elke beweerde fix is van het model, niet van Saikou.
Twee modi, twee regels
verify beoordeelt een beweerde fix en is streng: een sink die een beweerde fix overleeft, blokkeert. diff poort een gewone pull request en blokkeert alleen wat de wijziging introduceerde, zodat oude code nieuwe pull requests niet laat falen.

Er is geen score: bevindingen worden nooit opgeteld, want een getal wekt vertrouwen dat de checks niet hebben verdiend. En wat de auteur beweert is nooit bewijs - zegt een AI "ik heb de injectie opgelost", dan wordt dat vastgelegd als onbevestigde bewering.

Nieuwe analyzer-onderdrukking suppression_introduced

Een onderdrukkingsmarker (nosec, NOSONAR, lgtm of codeql[...], nosemgrep, noqa: S..., eslint-disable op een beveiligingsregel, usedforsecurity=False, ...) komt vaker voor dan eerst. Geteld per soort, dus een al onderdrukte regel aanpassen wordt niet gemeld. In Python tellen commentaarmarkers alleen in echt commentaar, waar bandit 1.7.3+, Sonar en CodeQL ze lezen; een marker binnen een string, zoals nepfix-testdata, telt niet. bandit 1.7.0-1.7.2 volgde daar wel een marker, dus de analyser-extra vereist 1.7.3. noqa en nosemgrep tellen overal op de regel, omdat flake8 en semgrep de ruwe regel lezen. Een woord vast aan een marker (nosecure) telt, omdat bandit het als kale marker leest, en een marker die pas na decoderen met de opgegeven broncodering zichtbaar wordt ook. usedforsecurity op iets anders dan True telt. Een marker die naar code zonder marker is verhuisd, terwijl het aantal markers gelijk blijft, wordt ook gemeld (in Python per statement). Python die niet te tokenizen is, wordt als tekst geteld. Bij wijzigingscontrole blokkeren alleen markers die een beveiligingsanalyzer het zwijgen opleggen; een kale noqa telt daarbij op een statement met een aanroep die bandit meldt (subprocess, eval, yaml.load, md5, pickle, ...), usedforsecurity op wachtwoordmateriaal, en overige type- en stijlmarkers worden een waarschuwing. In JavaScript en TypeScript tellen ook blokcommentaren, telt een ESLint-directive zonder regellijst als beveiligingsonderdrukking waar hij een regel met een risicovolle aanroep dekt (eval, new Function, child_process, fs, innerHTML, ...), wordt een naar een andere regel verhuisde marker gemeld, en is een TypeScript-directive een waarschuwing.

Gewijzigd bestand kon niet worden gecontroleerd content_not_checked

De nieuwe versie van een gewijzigd bestand in een taal die Saikou controleert (volgens de extensie of, bij een script zonder herkende extensie, volgens de #!-regel), of van een configuratiebestand van een analyzer, kon niet worden gecontroleerd: er staat een NUL-byte in de eerste 8 KB (UTF-16 en UTF-32 met een byte-order mark worden als tekst gelezen), het is groter dan 1.000.000 bytes, het kon niet uit de werkmap worden gelezen, of het pad is nu een symbolische link of een submodule. De wijzigingscontrole blokkeert zo'n bestand in plaats van het over te slaan. Anders zou elke wijziging in dat bestand ongecontroleerd doorgaan, door één NUL-byte in commentaar, door opvulling tot voorbij de grens, of door een symbolische link die door een bestand wordt vervangen. Is alleen de oude versie onleesbaar, dan wordt de nieuwe gecontroleerd alsof het bestand nieuw is. Een bestand dat zo hoort te zijn, zoals een grote meegeleverde bundel, laat je weg met een pathspec (-- . ':(exclude)vendor/bundle.js'); --warn-only content_not_checked maakt de check voor elk bestand een waarschuwing. Bestanden in talen die Saikou niet controleert, worden nog steeds overgeslagen en vermeld.

Gebruik

  1. Installeren
    pip install saikou

    Python 3.9 of nieuwer. De engine gebruikt alleen de standaardbibliotheek.

  2. Een beweerde fix controleren
    saikou verify before.py after.py --claimed-threats injection

    Streng: wat de fix zegt te repareren, moet gerepareerd zijn.

  3. Een pull request poorten
    saikou diff --base origin/main

    Controleert elk gewijzigd bestand en blokkeert alleen wat de wijziging introduceerde. Uitvoer als tekst, JSON of SARIF.

Vragen

Is Saikou een kwetsbaarhedenscanner?

Nee. Het beoordeelt wijzigingen: het vergelijkt de code vóór en na een fix en vraagt of de fix het ding veranderde waar het om ging. Houd je statische analyzer; Saikou controleert of fixes voor zijn bevindingen echt zijn.

Betekent "komt erdoor" dat mijn code veilig is?

Nee. Het betekent dat geen enkele check de wijziging blokkeerde. Saikou meldt wat het controleerde en hoe, en het certificeert niets. De grenzen zeggen waar het niet naar kijkt.

Wat is het verschil met een AI-tool die automatisch fixt?

Zo'n tool schrijft een fix. Saikou beoordeelt een fix, wie of wat hem ook schreef, en behandelt de beschrijving van de auteur als een onbevestigde bewering. Ze werken samen: laat de agent fixen, laat Saikou het resultaat controleren voordat het wordt gemerged.

Welke talen controleert het?

Python wordt aan beide kanten geparsed (ast_verified); met --analyser en bandit geïnstalleerd (pip install "saikou[analyser]") draait bandit mee, als extra bewijs. JavaScript en TypeScript krijgen structurele controles en de onderdrukkingschecks die getoetst zijn aan ESLint, de TypeScript-compiler en semgrep. Go, Java, C#, PHP, Ruby, Rust, C en C++, Kotlin, Swift, shell en SQL krijgen tekstuele checks (structural). Al het andere alleen basiscontroles (asserted). Elk rapport noemt het niveau per bestand.

Verlaat mijn code mijn machine?

verify, diff en de werkbank in de browser draaien lokaal en versturen niets. Alleen saikou harden stuurt code, naar de modelaanbieder die jij instelt, onder de voorwaarden van die aanbieder.

Waarom is er geen score?

Een getal wekt vertrouwen dat de checks niet hebben verdiend, en het verbergt welke check wat zei. Je krijgt bevindingen, elk met hoe ze is vastgesteld, en een oordeel per bestand.

Kan het een pull request tegenhouden?

Ja. saikou diff eindigt met 1 bij een hard fail, dus elke CI kan erop poorten; de GitHub Action doet dat voor je en kan zich beperken tot pull requests van bots of AI-agents.

Wat kost het?

Niets. De engine en elke koppeling zijn open source onder Apache-2.0. Betaalde abonnementen voor auditbewijs zijn gepland en nog niet te koop.

Wat Saikou niet doet

  • Het certificeert niets. Het meldt wat het controleerde en hoe - nooit dat code veilig is.
  • Het voert je code niet uit. Gedrag wordt structureel gecontroleerd (syntaxboom, API-oppervlak) voor Python, en voor andere talen helemaal niet.
  • Het is geen kwetsbaarhedenscanner. Het beoordeelt wijzigingen. Houd je SAST; Saikou controleert of fixes voor zijn bevindingen echt zijn.
  • Analyzer-bewijs is er alleen voor Python (bandit). Andere talen krijgen structurele checks, en elk rapport zegt dat.
  • Eén bestand tegelijk. diff controleert elk gewijzigd bestand, maar er is geen data-flow-analyse over bestanden heen.
