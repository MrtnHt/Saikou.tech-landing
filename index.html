Verify AI-written security fixes before you merge them.

An agent opens a pull request: "fixed the injection". The scanner agrees, because the agent added a nosec. Saikou compares the code before and after and blocks the fixes that only look fixed: a new suppression, a sanitised value nobody uses, one caller fixed while the shared sink stays raw, code replaced by // ... existing code ....

Why a clean scan is not proof

Static analysers honour suppression comments. So the cheapest way to make a finding disappear is to silence it, and a before/after comparison of findings then reports an improvement. Four steps, one of them a lie:

  1. The findingshell=True

    The scanner reports a command-injection risk.

  2. The "fix"+ # nosec B602

    The agent adds a suppression and changes nothing else.

  3. The scan afterfindings: 1 → 0

    The scanner skips the line, and the delta reads as a fix.

  4. SaikouBLOCKED

    It compares the code itself: the sink is unchanged and a suppression appeared.

Absence of a finding is never evidence of a fix.

How to read a report

Every finding is one line. This one is from the fake fix above:

HARD FAIL [parser] sink_shell_true L14: A fix for 'injection' was claimed but this sink survives unchanged: shell=True survives in the output; command injection sink intact.
HARD FAIL severity
A hard fail blocks the file. WARN is reported and does not block: something to look at, such as a type-checker directive. A file with at least one hard fail is BLOCKED, and the command exits with 1 (0 = no hard fail, 2 = error), so CI can gate on it.
[parser] how it was established
tool An external analyser (bandit) produced this, run twice: normally and with suppressions ignored.
parser Computed by parsing both versions into syntax trees and comparing them. Not a text guess.
mechanical A deterministic text or counting check. Reliable for what it looks for, blind to meaning.
sink_shell_true the check, and L14 the line
Every check has an id and a plain description; the full list is below. The line number points into the file after the change.
Verification tier, per file
ast_verified Python: both versions parsed; API surface and sinks computed, not claimed.
structural No parser: textual and structural checks only. Semantics are not verified.
asserted Unrecognised language: sanity checks only. Any claim of a fix is the model's, not Saikou's.
Two modes, two policies
verify judges a claimed fix and is strict: a sink that survives a claimed fix blocks. diff gates an ordinary pull request and only blocks what the change introduced, so old code does not fail new pull requests.

There is no score: findings are never added up, because a number invites trust the checks have not earned. And the author's claim is never evidence - if an AI says "I fixed the injection", that is recorded as an unverified claim.

New analyser suppression suppression_introduced

A suppression marker (nosec, NOSONAR, lgtm or codeql[...], nosemgrep, noqa: S..., eslint-disable on a security rule, usedforsecurity=False, ...) appears more often than before. Counted per marker kind, so editing a line that was already suppressed is not flagged. In Python, comment markers count only in real comments, which is where bandit 1.7.3+, Sonar and CodeQL read them; a marker inside a string literal, such as fake-fix test data, is not counted. bandit 1.7.0-1.7.2 did honour one there, so the analyser extra requires 1.7.3. noqa and nosemgrep still count anywhere on the line, because flake8 and semgrep match the raw line. A word glued to a marker (nosecure) counts, because bandit reads it as a bare marker, and so does a marker that only shows after decoding the declared source encoding. usedforsecurity set to anything but True counts. A marker moved onto code that had none, while the number of markers stays the same, is reported too (in Python, per statement). Python that does not tokenize is counted as text. In change gating only markers that silence a security analyser block; a bare noqa counts as one on a statement that makes a call bandit reports (subprocess, eval, yaml.load, md5, pickle, ...), usedforsecurity does on password material, and other type and style markers become a warning. In JavaScript and TypeScript, block comments count as well, an ESLint directive without a rule list counts as a security suppression where it covers a line that holds a risky call (eval, new Function, child_process, fs, innerHTML, ...), a marker moved onto another line is reported, and a TypeScript directive is a warning.

Changed file could not be checked content_not_checked

The new version of a changed file in a language Saikou checks (by its extension or, for a script without a recognised one, by its #! line), or of an analyser configuration file, could not be checked: it has a NUL byte in its first 8 KB (UTF-16 and UTF-32 with a byte-order mark are read as text), it is larger than 1,000,000 bytes, it could not be read from the work tree, or the path is now a symbolic link or a submodule. Change gating blocks such a file instead of skipping it. Otherwise one NUL byte in a comment, padding past the size limit, or a symlink swapped for a file would let any change in it through unchecked. When only the old version is unreadable, the new one is checked as if the file were new. A file that is meant to be like this, such as a large vendored bundle, can be left out with a pathspec (-- . ':(exclude)vendor/bundle.js'); --warn-only content_not_checked demotes the check for every file. Files in languages Saikou does not check are still skipped and listed.

Use it

  1. Install
    pip install saikou

    Python 3.9 or newer. The engine uses the standard library only.

  2. Check a claimed fix
    saikou verify before.py after.py --claimed-threats injection

    Strict: what the fix claims to repair has to be repaired.

  3. Gate a pull request
    saikou diff --base origin/main

    Checks every changed file, blocks only what the change introduced. Output as text, JSON or SARIF.

Questions

Is Saikou a vulnerability scanner?

No. It judges changes: it compares the code before and after a fix and asks whether the fix changed the thing that mattered. Keep your static analyser; Saikou checks that fixes to its findings are real.

Does "passes" mean my code is secure?

No. It means no check blocked the change. Saikou reports what it checked and how, and it certifies nothing. The limits say what it does not look at.

How is this different from an AI autofix tool?

An autofix tool writes a fix. Saikou judges a fix, whoever or whatever wrote it, and treats the author's description of the fix as an unverified claim. They work together: let the agent fix, let Saikou check the result before it is merged.

Which languages does it check?

Python is parsed on both sides (ast_verified); with --analyser and bandit installed (pip install "saikou[analyser]"), bandit also runs, as extra evidence. JavaScript and TypeScript get structural guard checks and the suppression checks tested against ESLint, the TypeScript compiler and semgrep. Go, Java, C#, PHP, Ruby, Rust, C and C++, Kotlin, Swift, shell and SQL get textual checks (structural). Anything else gets sanity checks only (asserted). Every report states the tier per file.

Does my code leave my machine?

verify, diff and the browser checker run locally and send nothing. Only saikou harden sends code, to the model provider you configure, under that provider's terms.

Why is there no score?

A number invites trust the checks have not earned, and it hides which check said what. You get findings, each labelled with how it was established, and a verdict per file.

Can it block a pull request?

Yes. saikou diff exits with 1 on a hard fail, so any CI can gate on it; the GitHub Action does this for you and can limit itself to pull requests opened by bots or AI agents.

What does it cost?

Nothing. The engine and every integration are open source under Apache-2.0. Paid plans for audit evidence are planned and not on sale yet.

What Saikou does not do

  • It certifies nothing. It reports what it checked and how - never that code is secure.
  • It does not run your code. Behaviour is checked structurally (syntax tree, API surface) for Python, and not at all for other languages.
  • It is not a vulnerability scanner. It judges changes. Keep your SAST; Saikou checks that fixes to its findings are real.
  • Analyser evidence is Python-only (bandit). Other languages get structural checks, and every report says so.
  • One file at a time. diff checks every changed file, but there is no cross-file data-flow analysis.
